# تحلیل و پیاده‌سازی پروژه فروشگاه آنلاین سوپرمارکت

## ۱. شرح کلی

این پروژه یک فروشگاه آنلاین سوپرمارکت با Django است که در آن مدیر فروشگاه محصولات را
با تمام مشخصات ثبت می‌کند و مشتریان پس از ثبت‌نام و احراز هویت پیامکی می‌توانند
دسته‌بندی‌ها و محصولات را مشاهده، جستجو، فیلتر و خریداری کنند.

## ۲. ساختار اپلیکیشن‌ها

پروژه طبق الزام صورت‌پروژه در قالب سه اپلیکیشن اصلی طراحی شده است:

### accounts (حساب کاربری)
مسئول ثبت‌نام، احراز هویت پیامکی (OTP)، ورود/خروج، پنل کاربری و ویرایش پروفایل.

### products (محصول)
مسئول دسته‌بندی محصولات، خود محصولات، ویژگی‌های هر محصول، امتیازدهی و نظرات،
جستجو و فیلتر، و پنل مدیریت محصولات/دسته‌بندی‌ها.

### orders (سفارش)
مسئول سبد خرید، ثبت سفارش، شبیه‌سازی پرداخت، پیگیری وضعیت سفارش و پنل مدیریت سفارش‌ها.

## ۳. مدل‌های دیتابیس (خلاصه)

**accounts**
- `User(AbstractUser)`: username, phone_number (یکتا), address, is_phone_verified
- `OTPCode`: phone_number, code (هش HMAC، نه متن ساده), created_at, is_used, attempts — با متد `is_valid()` (اعتبار ۲ دقیقه‌ای، حداکثر ۵ تلاش)

**products**
- `Category`: name, slug, description, image
- `Product`: category(FK), name, slug, brand, description, image, price, discount_percent,
  unit, stock, is_active — با پراپرتی‌های `final_price`، `average_rating`، `in_stock`
- `ProductFeature`: product(FK), key, value → پیاده‌سازی «ویژگی‌های مشخص» هر محصول
- `Review`: product(FK), user(FK), rating(1-5), comment — پیاده‌سازی امتیاز و نظر

**orders**
- `Cart` / `CartItem`: سبد خرید هر کاربر و آیتم‌های آن
- `Order`: user(FK), status(pending_payment/processing/shipped/delivered/cancelled),
  address, delivery_time, total_price → پیاده‌سازی پیگیری سفارش
- `OrderItem`: قیمت و تعداد هر محصول در لحظه‌ی خرید (ثبت مستقل از تغییرات بعدی قیمت)
- `Payment`: پرداخت از طریق زرین‌پال (amount, status, authority, transaction_id, paid_at)

## ۴. نگاشت نیازمندی‌های پروژه به پیاده‌سازی

| نیازمندی صورت پروژه | پیاده‌سازی |
|---|---|
| دسته‌بندی محصولات با ویژگی مشخص | مدل `Category` + `ProductFeature` |
| جستجوی محصولات | فیلد `q` در `product_list_view` (نام/توضیحات/برند) |
| فیلتر محصولات | فیلتر بر اساس دسته، بازه قیمت، مرتب‌سازی |
| جزئیات محصول | صفحه `product_detail` |
| امتیاز و نظر به محصول | مدل `Review` + فرم در صفحه جزئیات |
| سفارش محصول | `Order` + `OrderItem` |
| پیگیری سفارش | فیلد `status` + نمایش در `order_detail.html` |
| سبد خرید | `Cart` / `CartItem` + صفحات افزودن/ویرایش/حذف |
| ثبت‌نام | `RegisterForm` + `register_view` |
| احراز هویت پیامکی | `OTPCode` + `verify_otp_view` (کد در کنسول سرور شبیه‌سازی می‌شود) |
| پنل مدیریت | مسیرهای `/manage/...` با دسترسی `is_staff` در products و orders |
| پنل کاربری (مشتری) | `accounts:dashboard` — سفارش‌ها و ویرایش پروفایل |
| مقایسه محصولات (توسعه اختیاری) | لیست مقایسه بر پایه‌ی سشن (بدون نیاز به لاگین)، حداکثر ۴ محصول هم‌زمان، صفحه `products:compare` |

## ۵. صفحات وب‌سایت

**صفحات عمومی:** خانه، لیست محصولات (با فیلتر/جستجو)، جزئیات دسته‌بندی، جزئیات محصول،
مقایسه محصولات، ثبت‌نام، تایید کد پیامکی، ورود.

**پنل کاربری (نیازمند ورود):** داشبورد کاربر، ویرایش پروفایل، سبد خرید، تسویه‌حساب،
درگاه پرداخت (شبیه‌سازی)، لیست سفارش‌ها، جزئیات و پیگیری سفارش.

**پنل مدیریت (نیازمند is_staff):** لیست/افزودن/ویرایش/حذف محصول، لیست/افزودن دسته‌بندی،
لیست سفارش‌ها با فیلتر وضعیت، جزئیات سفارش و تغییر وضعیت.

همچنین پنل ادمین پیش‌فرض جنگو (`/admin/`) برای مدیریت کامل تمام مدل‌ها فعال است.

## ۶. نکات فنی

- زبان و جهت رابط کاربری: فارسی و RTL (Bootstrap RTL)
- هر تغییر قیمت محصول در سفارش‌های قبلی تأثیری ندارد چون `OrderItem` قیمت را در لحظه خرید ذخیره می‌کند.
- موجودی محصول (`stock`) هنگام **ثبت** سفارش رزرو (کم) می‌شود و با لغو/انقضای سفارش برمی‌گردد.
- احراز هویت پیامکی به‌صورت شبیه‌سازی‌شده پیاده شده (بدون اتصال به سرویس واقعی پیامک) تا پروژه
  بدون وابستگی به سرویس ثالث قابل اجرا و تست باشد؛ کد OTP در کنسول سرور چاپ می‌شود.
- درگاه پرداخت به‌صورت واقعی به **زرین‌پال** (Zarinpal، در حالت sandbox) متصل است
  (`orders/zarinpal.py`). اگر اتصال اینترنت به زرین‌پال در دسترس نباشد (مثلاً هنگام تست در
  محیطی بدون دسترسی خارجی)، سیستم به‌طور خودکار به یک صفحه‌ی پرداخت شبیه‌سازی‌شده سقوط
  می‌کند تا کل جریان سفارش همچنان قابل تست باشد.
- داده‌های نمونه (۵ دسته‌بندی و ۱۲ محصول) واقعی و با نام‌های برند واقعی بازار ایران ثبت شده‌اند.

## ۷. نحوه اجرا

```
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

کاربر ادمین نمونه: `admin` / رمز: `Admin@12345` (شماره موبایل: 09120000000)

## بازبینی و بهبودها (نسخه‌ی تقویت‌شده)

| حوزه | تغییر |
|---|---|
| امنیت پرداخت | شبیه‌سازی پرداخت فقط در DEBUG و فقط با POST؛ بررسی تطابق Authority در callback |
| موجودی | قفل `select_for_update` + رزرو هنگام ثبت سفارش، آزادسازی با لغو/انقضا، کنترل موجودی در سبد |
| پایداری | ثبت سفارش در `transaction.atomic`؛ تایید پرداخت سه‌حالته؛ دستورات `reconcile_payments` و `expire_pending_orders` |
| OTP | `secrets` + ذخیره‌ی هش + محدودیت تلاش + ارسال مجدد + حساب غیرفعال تا تایید + پاکسازی کاربران تاییدنشده |
| CSRF / HTTP | تغییر وضعیت‌ها فقط POST؛ جلوگیری از open redirect در بازگشت به صفحه‌ی قبل |
| تنظیمات | SECRET_KEY و مرچنت‌کد از `.env`؛ تنظیمات امن production؛ `.gitignore`؛ حذف `db.sqlite3` و `db_output.json` از پروژه |
| کارایی | حذف N+1 (امتیاز محصولات با annotate، `select_related` در سبد/سفارش‌ها)، pagination در پنل‌ها |
| مقایسه | فقط هم‌دسته، حفظ لیست پس از خروج، مرتب‌سازی O(n) |
| داده | محصول استفاده‌شده در سفارش حذف نمی‌شود (غیرفعال می‌شود) |
| پرداخت | تاریخچه‌ی Authority (`PaymentAuthority`)؛ پرداخت روی کد قدیمی‌تر هم پذیرفته و تطبیق داده می‌شود؛ پنجره‌ی تطبیق کوتاه‌شده |
| ورود و سفارش‌ها | سقف نرخ تلاش ناموفق ورود؛ سفارش پرداخت‌شده نه به pending برمی‌گردد و نه توسط cron لغو می‌شود |
| یکپارچگی داده | `Order.user` با `PROTECT`؛ حذف کاربر سابقه‌ی مالی را پاک نمی‌کند |
| ثبت‌نام | سقف نرخ (IP / شماره / تایید کد)؛ ثبت‌نام ناتمام شماره را قفل نمی‌کند؛ ارقام فارسی نرمال می‌شوند |
| فرانت‌اند | Bootstrap و فونت محلی (بدون CDN)؛ تصویر پیش‌فرض SVG محلی؛ پیام‌های خطا با کلاس `alert-danger` |
| کیفیت | ۱۱۷ تست خودکار + GitHub Actions |
